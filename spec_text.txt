1.4 Infrastructure &amp; Scalability
Concurrent Connection Planning
Firebase RTDB on the Blaze plan supports up to 200,000 concurrent connections per database instance, but the default limit is lower and must be raised explicitly before launch. Capacity planning must be done before architecture is finalised.
Define peak concurrent user target before Week 2 — even a rough cap (e.g. max 20 simultaneous rooms × 50 players = 1,000 connections) determines whether sharding is needed.
If demand exceeds one RTDB instance, shard by room: create one RTDB instance per active game room. Firebase supports multiple named DB instances per project.
Model RTDB read fan-out: N players × M number calls per game × average session length = total download volume per month.
Cloud Functions Cold Starts
Cloud Functions on the critical game path (card purchase, win validation, prize crediting) can experience 1–3 second cold starts. Mitigation:
Set minimum-instances = 1 on card-purchase, win-validate, and prize-credit functions to keep them warm.
Estimated cost: ~$5–15/month per kept-warm function — justified for game-critical paths.
Non-critical functions (bonus crediting, referral tracking) can remain cold-start.

2.2 Bingo Card Generation
Cards per Player: Up to 6 cards per session — each card purchased separately at the entry fee
Card Range: Classic 1–75 number grid (5×5, centre FREE)
Card Assignment: Randomly generated server-side per player per session — uniqueness guaranteed within a room
Card Generation Algorithm
Each column is populated using the standard Bingo column-range convention:
B: 1–15  |  I: 16–30  |  N: 31–45  |  G: 46–60  |  O: 61–75
For each column, draw 5 numbers (4 for N column — centre is FREE) without replacement from that column&apos;s range using Fisher-Yates shuffle seeded by crypto.randomInt.
Uniqueness within a room: after generation, compare the card&apos;s ordered number sequence against all existing cards in the room. If a collision is detected, regenerate. Expected collision probability is negligible for rooms under 200 players.
Card fingerprint (SHA-256 of ordered number array) stored server-side per session for audit.

2.4 Win Detection &amp; Edge Cases
Detection Order
Win patterns are evaluated server-side after every number call, in tier order (Line → Corners → Full House). This prevents a Full House from being credited before a Line is claimed.
Simultaneous Winners
Multiple players with a winning pattern on the same call split that tier&apos;s prize equally.
Prize split is calculated in integer santim (see §5.6). Any indivisible remainder is added to the next-highest tier&apos;s prize pool.
Example: 1st Win prize = 10,200 santim (102 ETB), 3 simultaneous winners → 3,400 santim each. Zero remainder.
Example: 1st Win prize = 10,300 santim, 3 winners → 3,433 / 3,433 / 3,434 santim. The 1-santim remainder goes to the player whose card fingerprint is lexicographically last (deterministic, auditable).
All-Tiers-Simultaneous
If a single call triggers all three tiers simultaneously (theoretically possible on the last number of a Full House game), tiers are credited in sequence: Line winner(s) → Corners winner(s) → Full House winner(s). Server processes them in a single Firestore transaction.
2.5 Room Types
Open Lobby: Players join anytime — game starts the moment 2 or more players are in the room
Scheduled Tournaments: Fixed start times set by operator (e.g. 8PM, 10PM daily); countdown timer visible in lobby
Minimum Players: 2 players required to start any game. High-stake rooms (Gold 100 ETB) require a minimum of 5 players to reduce collusion risk (see §4.5)
Unfilled Scheduled Rooms: Operator decides per room: cancel with full refund to wallet, or start with present players
2.6 Disconnection Handling
A player losing network connectivity during a live game must not result in a lost win or a locked game state.
Server-side card marking continues automatically — the player&apos;s card is marked by the Cloud Function on every number call, regardless of client connectivity.
On reconnect, the client receives the full game state diff since disconnection via RTDB.
If a win occurs on a disconnected player&apos;s card: the win is credited to their wallet exactly as if they were connected. They receive a push notification.
If a player is disconnected for more than 90 seconds, their presence record in RTDB is removed via .onDisconnect(). Their cards remain active for the duration of the game.
Operator dashboard shows &apos;disconnected&apos; status per player in real-time game view.

Referral Bonus requires the referred user to complete at least one full paid game, preventing deposit-and-withdraw cycles.
Velocity rule: accounts that claim a bonus and request withdrawal within 60 minutes without playing a game are auto-flagged for admin review.

4. Security &amp; Fraud Prevention
This section defines all security controls for the platform. These requirements are non-negotiable and must be implemented before beta launch.
4.1 Identity &amp; Account Security
Multi-Accounting Prevention
Phone number is the unique identity anchor — one account per OTP-verified number.
Device fingerprinting on registration (FingerprintJS or equivalent). Flag accounts sharing a device fingerprint with an existing account for admin review; do not auto-block (shared phones are common).
If a flagged device creates a second account and claims a bonus within the first session, auto-suspend the newer account and notify admin.
Session Security
Firebase Auth JWT tokens expire after 1 hour — client must handle silent token refresh.
All Cloud Function endpoints verify Firebase Auth ID token on every invocation. Client-side state is never trusted for financial operations.
Firestore Security Rules: players can only read/write their own user document, wallet, and cards. Cross-player reads are prohibited. Admin reads are gated by a custom claim role field.
Admin panel enforces a separate Firebase Auth tenant (or project) from the player app — admin credentials cannot be used in the player app.
4.2 RNG Integrity &amp; Audit Trail
Algorithm Specification
Mode A (Auto Generate) uses Node.js crypto.randomInt, which wraps the OS CSPRNG (urandom on Linux). This is cryptographically secure and does not require a third-party library.
Commit-Reveal Scheme
To allow post-game auditability by players and regulators, the following protocol is used:
Before a game starts: generate the full number sequence for the session. Compute SHA-256 of the sequence. Store seed, sequence, and hash in Firestore (write-once, append-only collection).
Publish the hash to all players at game start (visible in game UI as &apos;Game ID / Seed Hash&apos;).
After the game ends: reveal the full sequence. Any player can verify SHA-256(revealed sequence) == published hash.
This provides provably fair verification without requiring a third-party RNG audit service at launch.

4.3 Fraud Detection &amp; Win Verification
Automatic Win Flagging Criteria
Wins matching any of the following criteria are held for operator review before wallet credit:
Player wins more than 3 games in a rolling 6-hour window across any room.
Player&apos;s win rate in the last 20 games exceeds 30% (statistically improbable at scale).
Multiple wins claimed from the same device fingerprint within one 24-hour period across different accounts.
First-time depositor wins on their very first game (high bonus-abuse signal — review, do not auto-block).
Game had fewer than 4 unique player device fingerprints (possible collusion ring).
Operator SLA for Flagged Wins
Flagged wins must be reviewed within 30 minutes of flagging. If no operator action is taken within 30 minutes, the win is auto-approved and credited, with a permanent audit log entry noting the auto-approval. This prevents legitimate winners from being blocked indefinitely.

4.5 Collusion Detection
A minimum of 2 players can start a game. At this minimum, coordinated play can create a near-guaranteed win loop. The following controls mitigate this:
Gold tier rooms (100 ETB) require a minimum of 5 players to start. Silver tier requires 3. Bronze tier minimum remains at 2.
Flag for admin review: any two accounts that have played together in more than 10 games in a 7-day period.
Flag for admin review: rapid deposit-then-withdrawal cycles (deposit → play → withdraw within 2 hours, profit &gt; 0) across multiple sessions.
Admin dashboard provides &apos;co-play graph&apos; view: shows which player accounts frequently appear in the same room.

5.2 Webhook Security
Payment gateways notify the platform of completed deposits via HTTP webhooks. An unsecured webhook endpoint allows an attacker to POST a fake deposit confirmation and credit arbitrary wallet balances.
Required Implementation
Each gateway provides an HMAC secret key during merchant onboarding. Store these in Firebase Secret Manager — never in code or environment variables committed to version control.
On every incoming webhook: compute HMAC-SHA256(raw request body, gateway_secret) and compare to the signature in the webhook header. Reject any request where signatures do not match — return HTTP 400 and log the attempt with source IP.
Webhook endpoints must only accept POST requests from the gateway&apos;s documented IP ranges (whitelist at Cloud Function or GCP firewall level).
Log every incoming webhook: gateway, transaction_id, signature_valid (bool), processing_result, timestamp.
5.3 Idempotency Design
Network instability or gateway retry logic can cause the same webhook to fire multiple times for a single transaction. Without idempotency controls, a single deposit can credit the wallet twice.
Required Implementation
Each gateway transaction has a unique transaction_id in the webhook payload. Store this as a document ID in a Firestore &apos;processed_webhooks&apos; collection on first successful processing.
On every webhook receipt: attempt to create the Firestore document using the transaction_id as the document ID. If the create fails (document already exists), the webhook is a duplicate — return HTTP 200 (acknowledge receipt) without processing and log as duplicate.
Use a Firestore transaction (atomic read-check-write) when crediting the wallet to guarantee race-condition safety if two webhook calls arrive simultaneously.
The &apos;processed_webhooks&apos; collection is append-only and serves as the canonical deposit ledger.
5.4 iOS Safari Payment — Failure Handling
The iOS payment flow uses @capacitor/browser to open a Safari sheet. The user may close the sheet mid-payment, force-quit the app, or lose connectivity before the app receives a return callback.
Required Implementation
Before opening the browser sheet: write a &apos;pending_payment&apos; record to Firestore with the gateway, amount, and a unique payment reference ID.
On app resume after browser sheet close (App.addListener(&apos;appStateChange&apos;) or Browser.addListener(&apos;browserFinished&apos;)): query the gateway&apos;s transaction status API using the payment reference ID.
Show a &apos;Checking payment status…&apos; screen during the status query — never assume success or failure before querying.
If gateway confirms payment successful but wallet is not yet credited: the pending_payment record is picked up by a scheduled Cloud Function reconciliation job (runs every 5 minutes) and credited.
If gateway confirms payment failed or cancelled: dismiss the pending_payment record and notify the user.
If the status query fails (network unavailable): leave the pending_payment record open. It will be caught by the next reconciliation run.
5.5 Transaction Reconciliation
Four gateways with independent settlement cycles will produce discrepancies between gateway records and internal wallet records over time. A reconciliation process is required.
Scheduled Cloud Function runs daily at 02:00 EAT: download the prior day&apos;s settlement report from each active gateway API.
Compare each gateway transaction_id against the processed_webhooks Firestore collection.
Flag mismatches to admin dashboard: gateway records a successful transaction not found in processed_webhooks (missed credit) or vice versa (phantom credit).
Admin resolves flagged items manually. Audit log entry required for every manual reconciliation action.
Monthly reconciliation summary report exported to admin dashboard (total deposits per gateway vs. total wallet credits).
5.6 Monetary Arithmetic — Integer (Santim) Model
All financial values are stored and calculated in integer santim (1 ETB = 100 santim). JavaScript floating-point arithmetic must never be used for monetary calculations.
All entry fees, wallet balances, pot values, prize amounts, house cuts, and bonus values are stored as integer santim in Firestore.
Display layer only: convert santim to ETB for UI display (santim / 100, formatted to 2 decimal places). Never store or calculate using the display value.
Prize split calculation: (total_pot_santim * prize_percentage_numerator) / prize_percentage_denominator — use integer division throughout. Remainder allocation is defined in §2.4.
Withdrawal amounts: player enters ETB in UI, convert to santim on submission, validate as integer, store as integer.
Example: 10 ETB entry fee = 1,000 santim. 15% house cut = 150 santim. 85% player pool = 850 santim. Line prize (20%) = 170 santim = 1.70 ETB.

6.1 Authentication &amp; Access Control
Authentication Requirements

Admin panel login is restricted to a pre-approved IP allowlist (operator office IPs). Login attempts from outside the allowlist are rejected with HTTP 403.
Failed login attempts: 5 consecutive failures locks the account for 30 minutes and sends an alert to the super-admin email.

9. Compliance &amp; Legal
This section identifies legal and regulatory obligations. JAN Solutions is responsible for implementing the technical controls listed below. Legal interpretation and licence applications are the client&apos;s responsibility.
9.1 Gambling Licensing
Bingo for real money in Ethiopia is a regulated activity. The platform must not accept deposits or run paid games until the client confirms that the required licence or authorisation from the relevant Ethiopian authority (currently the Ethiopian Revenues and Customs Authority / National Lottery Administration) is in place.
Technical control: a platform-level kill switch in Firestore config allows the Super-Admin to disable all real-money game creation and deposits instantly, without a deployment. This must be implemented in Week 1.
9.2 Age Verification
Gambling platforms must restrict access to adults. The minimum age for gambling in Ethiopia is 18.
Players must declare their date of birth at registration. The platform must reject registrations that calculate to under 18 years old.
Date-of-birth is stored and flagged if inconsistent with KYC documents (when KYC is implemented).
Age verification is a registration-time check only at launch — full KYC document verification is a post-launch enhancement.
9.3 Anti-Money Laundering (AML)
The platform handles cash-equivalent value and must apply basic AML controls.
Transaction monitoring: flag any single deposit &gt; 10,000 ETB or aggregate deposits &gt; 50,000 ETB in a 30-day period for admin review.
Withdrawal monitoring: flag withdrawal requests within 2 hours of deposit where the player&apos;s net gaming activity shows no or minimal game play.
Record-keeping: all deposit, withdrawal, and win records must be retained for a minimum of 7 years in Firestore with no deletion capability below Super-Admin level.
9.4 Data Protection
The Ethiopian Personal Data Protection Proclamation (2022) applies to this platform.
Player personal data (name, phone, DOB, transaction history) is stored only in Firebase (GCP), which offers data residency options — confirm with client whether data must be hosted in-region.
Privacy Policy and Terms &amp; Conditions must be displayed at registration and linked in app footer. These must be drafted by the client&apos;s legal counsel before launch.
Players must have a mechanism to request account deletion. Implement a &apos;Delete My Account&apos; flow that anonymises personal data while retaining financial records for AML compliance.
